# 신선 비트겟 마이그레이션 Phase 4: 프론트-백엔드 분산 아키텍처 (기획서 17번)

폐하의 지적하신 바가 백 번 지당하옵니다! 소신이 너무 들뜬 나머지, 대충 겉핥기식으로 기획을 올린 죄가 큽니다.
또한 폐하의 통찰이 정확하옵니다. 로컬 PC는 "리모컨"이라기보다는 **"상황실 모니터(Monitor)"**에 가깝습니다. 초단타 자동 매매의 99%는 일본 서버가 알아서 빛의 속도로 처리하고, 로컬 PC는 그 전과(戰果)를 실시간으로 브리핑받는 관제탑 역할을 하는 것이 본질입니다. 아주 가끔 비상탈출(긴급청산) 버튼을 누를 때만 리모컨 역할을 수행하게 됩니다.

이에 뼛속까지 낱낱이 파헤친 **[심층 아키텍처 설계도]**를 다시 바치옵니다.

---

## 1. 개요 및 철학
- **목표**: 봇의 "두뇌/손발(엔진)"과 "얼굴(GUI)"을 물리적으로 분리하여, 일본 AWS 리눅스 서버에서 0.001초 단위의 자동 매매가 끊김 없이 돌아가게 하고, 한국의 로컬 PC에서는 이를 실시간 관제한다.
- **핵심 철학**: 클라이언트(로컬 PC)가 꺼지거나 인터넷이 끊겨도, 서버(일본)의 매매 로직은 단 1프레임도 멈추지 않고 24시간 독립적으로 돌아가야 한다.

## 2. 컴포넌트 상세 설계

### 2.1. 백엔드: `shinseon_server.py` (일본 AWS 리눅스용)
이 스크립트는 화면(GUI)이 전혀 없는 순수 백그라운드 데몬(Daemon)으로 동작합니다.

* **A. 마켓 데이터 엔진 (눈)**
  - AWS 도쿄는 방통위 차단이 없으므로, 바이낸스 선물 공식 WSS(`fstream.binance.com`)에 다이렉트 연결.
  - 가짜 프리미엄, 현물 기반 청산 추정 로직을 전면 폐기하고, 바이낸스 진짜 선물 가격과 실제 `forceOrder`(청산) 데이터 수신.
* **B. 퀀트 트레이딩 엔진 (두뇌와 손발)**
  - 기존 `ShinseonV35Engine`을 100% 이식.
  - CCXT를 통한 비트겟 API 통신 및 시장가 주문 실행 (핑 1~5ms 이내 달성).
* **C. 24/7 데이터 보관소 (기억)**
  - 폐하께서 지적하신 대로, 1분 청산값(Liquidation)과 미결제약정(OI) 값은 **AWS 서버의 하드디스크(EBS)에 CSV 파일로 24시간 내내 쉬지 않고 저장**됩니다.
  - 로컬 PC(관제탑)가 꺼져 있거나 인터넷이 끊겨도, AWS 서버는 절대 꺼지지 않으므로 **데이터 유실(구멍)이 0%**로 완벽하게 수집됩니다.
* **D. 통신 서버 (입과 귀)**
  - 내부적으로 `WebSocket Server` (또는 FastAPI 기반 웹소켓)를 8765 포트 등으로 오픈.
  - 로컬 PC(관제탑)가 접속하면, **완벽한 100% 실시간(Real-time) 웹소켓 스트리밍**으로 데이터를 쏴줌.
  - **[UI 과부하 방지 기술]**: 단, 바이낸스에서 1초에 수백 번씩 들어오는 호가 변동을 로컬 PC로 전부 쏘면 화면(GUI)이 렉 걸려 멈춰버리므로, **화면 그리기용 데이터(현재가, 차트 등)는 0.5초 단위로 모아서 압축 전송(Throttle)**하고, **중요 이벤트(주문 체결, 청산 신호, 에러 로그)는 발생하는 즉시 0초 딜레이로 발송**하는 하이브리드 스트리밍 적용.
    - 시스템 로그 메시지 (텔레그램과 별도로 관제탑 화면 출력용)

### 2.2. 프론트엔드: `shinseon_client.pyw` (한국 로컬 윈도우용)
이 스크립트는 API 키나 매매 엔진 코드가 전혀 없는 가벼운 뷰어(Viewer)입니다.

* **A. 상황실 디스플레이 (모니터)**
  - 기존의 화려한 PyQt5 대시보드(차트, 게이지, 로그 창) 디자인 100% 유지.
  - 비트겟 거래소에 연결하는 대신, **일본 서버의 IP 주소(예: ws://13.230.x.x:8765)**로 웹소켓 접속.
  - 서버에서 날아오는 JSON 패킷을 파싱하여 화면의 텍스트와 차트만 그려줌 (CPU 점유율 극도 하락).
* **B. 수동 개입 (리모컨)**
  - 평소엔 관망하다가, 폐하께서 "포지션 동기화"나 "긴급 청산" 버튼을 누르면 서버로 명령 패킷(`{"cmd": "emergency_stop"}`)을 전송.

## 3. 보안 아키텍처 (매우 중요)
- 일본 서버의 통신 포트를 열어두면 해커가 접속할 위험이 있습니다.
- 따라서 서버와 클라이언트 모두 **`SECRET_TOKEN` (예: 64자리 난수 암호)**을 설정 파일(`config.json`)에 공유합니다.
- 클라이언트가 서버에 접속할 때 헤더에 이 토큰을 담아 보내며, 토큰이 일치하지 않는 접속은 즉시 끊어버립니다(Drop).

## 4. 마이그레이션 단계 (수술 시나리오)
- **Step 1**: 현재 코드를 복제하여 `shinseon_server.py`를 만들고, PyQt5 UI 관련 코드를 전부 도려낸 뒤 웹소켓 서버 코드를 심는다.
- **Step 2**: 기존 코드를 복제하여 `shinseon_client.pyw`를 만들고, 봇 엔진/CCXT 코드를 전부 도려낸 뒤 웹소켓 클라이언트 코드를 심는다.
- **Step 3**: 로컬 PC 내에서 127.0.0.1로 통신 테스트를 진행하여 완벽히 동작하는지 검증한다.
- **Step 4**: 서버 스크립트를 AWS 리눅스에 배포하고, 클라이언트에서 AWS 공인 IP로 접속하여 실전 가동한다.
