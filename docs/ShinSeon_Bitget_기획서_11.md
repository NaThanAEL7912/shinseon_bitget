# 신선 비트겟 (ShinSeon_Bitget) 기획서 11 - 보안 및 아키텍처 정밀 진단 보고서

폐하의 하명에 따라 소신(PM)이 매서운 눈으로 현재 소스코드(`shinseon_master_app.pyw`)의 보안 상태와 향후 엔진 이식(Phase 2) 시 반드시 짚고 넘어가야 할 아키텍처 이슈를 전수 조사하였나이다.

## 1. 보안(Security) 진단: [통과 - 매우 우수]
- **API 키 유출 방어**: 코드를 샅샅이 뒤져본 결과, `.env`에서 불러온 `BITGET_API_KEY` 등이 로그(`add_log`)나 터미널 화면(`print`), 텔레그램 메시지 등으로 노출되는 취약점은 단 하나도 발견되지 않았사옵니다.
- **메모리 내 안전 캡슐화**: 키값은 오직 `ccxt.bitget({...})` 객체 초기화 시 한 번만 주입되며, 이후에는 메모리 내부에서만 안전하게 암호화되어 통신에 사용되옵니다.

## 2. Phase 2 (엔진 이식)를 위한 핵심 보완(수정) 사항
기존 BBITGET(Playwright 브라우저 클릭) 방식에서 **Bitget 공식 API(ccxt)** 방식으로 넘어오면서 새롭게 대비해야 할 세 가지 중대 사안을 발견하였나이다.

### 2.1. API 전용 예외(Exception) 처리 방어벽 구축
브라우저 매크로는 단순히 '클릭 실패(Timeout)'로 끝나지만, API 통신은 다양한 에러를 뱉어냅니다. 
- 잔고 부족 (`ccxt.InsufficientFunds`)
- 비트겟 서버 점검/응답 지연 (`ccxt.NetworkError`)
- **수정 계획**: 엔진 수술 시, 주문(Order) 함수 전체에 철저한 `try...except` 방어벽을 둘러서 봇이 멈추지 않고(Crash 방지) 폐하의 텔레그램으로 즉각 "주문 실패 경고"를 쏘도록 설계하겠사옵니다.

### 2.2. Rate Limit (API 호출 한도) 초과 대비
비트겟 선물 API는 1초당 주문 횟수에 제한이 있사옵니다. 만약 청산 폭포수가 쏟아져 분할 진입 시그널이 1초 내에 수십 개가 터진다면 IP 차단을 당할 수 있사옵니다.
- **수정 계획**: 이미 1차 뼈대 공사에서 `enableRateLimit: True` 옵션을 켜두어 ccxt 자체적으로 속도 조절을 하게 만들었사오나, 추가로 엔진 자체에서도 비동기 딜레이(`asyncio.sleep(0.05)`)를 미세하게 주어 안전성을 극대화하겠습니다.

### 2.3. 비동기 블로킹(Blocking) 억제
주문을 넣을 때 서버 응답을 기다리느라 바이낸스의 실시간 시그널(웹소켓) 수신이 밀리면 안 되옵니다.
- **수정 계획**: `create_order` API 호출 시 반드시 `asyncio.create_task()` 형태의 백그라운드 던지기(Fire-and-Forget) 방식으로 구현하여 시그널 수신에 단 0.001초의 딜레이도 주지 않겠습니다.
